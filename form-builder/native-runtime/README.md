# FormLogic Native Runtime

A generic **Tauri v2** desktop/mobile shell that loads a FormLogic app into a native window and
exposes a small, approved set of native capabilities over `window.FormLogicNative` — a **connector
registry** (the phone's own abilities + device/vehicle data) and an **offline sync queue**. The web
runtime feature-detects the bridge, so the same app gains native powers with no code change.

> Design: `../../docs/NATIVE_RUNTIME_TAURI.md`. Connectors: `../../docs/CUSTOM_APP_PLATFORM.md#connectors`.
> This runtime is generic (`com.formlogic.runtime`), not app-specific.

## How it works

The runtime holds **no app of its own**. It opens a hosted FormLogic app into its window and gets
out of the way — the app takes over the whole screen and inherits the bridge.

- **Empty shell.** With no app loaded it shows a minimal, branded placeholder ("No app loaded" +
  "open from a link or domain"). There is **no URL entry** and no demo panels — apps arrive only via
  links (below).
- **Open via a link.** Tapping a FormLogic app link opens it straight in the runtime — see
  **Deep links** below. No typing.
- **Reopen the last app.** The runtime remembers the last-opened app (`localStorage['fl.lastApp']`)
  and **auto-reopens it** on launch, so it behaves like a dedicated app. Escape a broken remembered
  app with a `formlogic://home` link or a rapid double-launch (both return to the placeholder).
- **Loading experience.** Opening/reopening an app shows a **branded FL spinner** and nothing else —
  never the shell, never a white flash. The Android system splash + window background are the runtime
  navy; the shell boots straight into the loader; and the bridge injects a matching spinner into the
  app page until it actually paints (so the hosted app's own loading screen is covered too).

## Capabilities (the bridge)

`window.FormLogicNative` is injected into **every page** in the window — the shell *and* any FormLogic
app it navigates to — so app-logic / SDK screens call the same API in-browser and native:

- **Connectors** — the app asks for abstract commands and doesn't care about the transport:
  - **`device`** — the **phone's own abilities** (GPS, battery, network, device info, screen,
    orientation/motion, clipboard, wake-lock, vibrate). Implemented with the WebView's **Web APIs**,
    **feature-detected at runtime** (no native plugin), so it works identically in a browser, the
    PWA, and the native runtime. See `docs/CUSTOM_APP_PLATFORM.md#connectors`.
  - **`vehicle`** — a Rust mock returning realistic telemetry (same shape as the browser mock), so
    QuickJS `onConnectorEvent` mapping is identical everywhere.
- **Offline sync queue** — flushes to the same idempotent `POST /api/app/{slug}/sync/batch` endpoint
  the browser uses.

## Deep links — "open in app" without typing a URL

The runtime registers as a handler for FormLogic app links (spec §26):

- **Custom scheme** `formlogic://open?url=<url-encoded app url>` — works with **no** domain
  verification (self-hosted / local / QR codes).
- **https App Links** `https://formlogic.com/open/...` — verified against
  `/.well-known/assetlinks.json` on the host; the OS opens the app straight from a normal web link.

Both are generated by `tauri-plugin-deep-link` from `tauri.conf.json > plugins.deep-link`. Only
`http`/`https` targets are ever navigated to — `javascript:`/`file:`/etc. are rejected. On **cold
start** the launch target is stashed and opened once the shell loads; **warm** links navigate the
open window immediately (Android `singleTask` `onNewIntent`). Test on an emulator:

```bash
adb shell am start -a android.intent.action.VIEW \
  -d "formlogic://open?url=http%3A%2F%2Flocalhost%3A8090%2Fapp%2F<slug>"
```

## Layout

```
src/                     shell frontend: branded loader + "no app loaded" placeholder (main.ts, index.html, styles.css)
src-tauri/
  src/lib.rs             Rust commands (runtime_info, connector_*, sync_*, pending_deep_link) + mock vehicle
                         connector + bridge init-script (window.FormLogicNative + destination loading overlay)
                         + deep-link handling (open/warm/cold, scheme validation)
  tauri.conf.json        withGlobalTauri; window built in setup() to carry the init script; deep-link plugin config
  capabilities/          IPC grants incl. remote.urls for approved FormLogic origins + deep-link:default
  gen/android/           Tauri-generated Android Gradle project (themes = fl_navy splash; build outputs gitignored)
```

## Prerequisites

- **Rust** (`cargo`) + `rustup`
- Desktop: a system WebView — WebView2 (Windows 11), WebKitGTK (Linux), WKWebView (macOS)
- Android: `ANDROID_HOME`, an NDK (r26/r27), a JDK 17–21 (the Android Studio JBR works), and the
  Rust Android targets:
  `rustup target add aarch64-linux-android x86_64-linux-android armv7-linux-androideabi i686-linux-android`

## Develop

```bash
npm install
npm run tauri dev          # launches the desktop window against the Vite dev server
cd src-tauri && cargo test # headless unit tests (connector + deep-link parsing)
```

## Build — desktop

```bash
npm run tauri build        # installers under src-tauri/target/release/bundle/ (MSI + NSIS on Windows)
```

## Build — Android

```bash
npm run tauri android init
npm run tauri android build --apk --debug -t x86_64   # emulator; use -t aarch64 for devices
```

**Windows gotcha:** `tauri android build` symlinks the compiled `.so` into
`gen/android/app/src/main/jniLibs/<abi>/`, which needs Developer Mode/admin ("Creation symbolic link
is not allowed"). Either enable Windows Developer Mode, or after the Rust compile finishes strip the
lib (it also shrinks a debug lib from ~120 MB to ~19 MB so it fits the emulator) and package via
Gradle directly:

```powershell
llvm-strip --strip-all src-tauri\target\<abi>-linux-android\<profile>\libnative_runtime_lib.so
copy   …\libnative_runtime_lib.so   src-tauri\gen\android\app\src\main\jniLibs\<abi>\
cd src-tauri\gen\android
.\gradlew.bat assemble<Abi><Debug|Release> -x rustBuild<Abi><Debug|Release> --rerun-tasks
adb install -r app\build\outputs\apk\<abi>\<profile>\app-<abi>-<profile>.apk
adb shell am start -n com.formlogic.runtime/.MainActivity
```

The frontend is embedded in the `.so` (via `generate_context!`), so the APK is self-contained.

### Release signing (Android)

`app/build.gradle.kts` reads `gen/android/keystore.properties` (gitignored) and signs `release`
builds. Generate a keystore once with `keytool -genkeypair -keystore formlogic-release.jks -alias
formlogic -keyalg RSA -keysize 2048 -validity 10000`, point `keystore.properties` at it, build a
release `.so` + package `assemble<Abi>Release`, then verify with
`apksigner verify --print-certs <apk>`.

> **Secrets:** the keystore (`*.jks`) and `keystore.properties` are gitignored and must never be
> committed. Use a securely-stored keystore + CI secrets for production releases.

## Verified

- **Windows desktop**: MSI + NSIS installers; app runs, bridge connects, connector round-trips.
- **Android** (x86_64 emulator), debug **and** signed release: APK installs, bridge connects
  (`platform: android`), vehicle telemetry round-trips.
- **Deep links** (cold + warm): a `formlogic://` link opens the runtime straight into an app; a
  malicious `javascript:` target is rejected.
- **Device connector**: returns real phone data in the runtime (device info, network, battery, …)
  via the `/device-check` page.
- **Loading**: navy FL splash → FL spinner → app, no white flash and no shell flash.
- `cargo test`: connector telemetry shape + command routing + deep-link target parsing/validation.

## Security

- Only signed FormLogic apps on approved origins get bridge access (remote-IPC allowlist in
  `capabilities/`, plus signed [client manifest](../../docs/CUSTOM_APP_PLATFORM.md#client-manifest)
  verification as a follow-up). Arbitrary PWAs can render but cannot touch connectors.
- Deep links open **http/https targets only** — `javascript:`/`file:`/`data:` are rejected, so a
  crafted link can't execute in the privileged shell origin. The `device` connector's phone-ability
  access is gated per-command by app-logic permissions (`connector.device.<cmd>`), and device I/O
  runs in the trusted web layer, never inside the QuickJS sandbox.
